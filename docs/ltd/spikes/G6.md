## متن پیشنهادی (انگلیسی)

**Title:** Proposal: RTL support + Persian (fa) locale, and optional goal hierarchy (`parent_goal_id`), with working spikes

Hi @chrisvel and everyone,

I'm building a personal planning setup on top of tududi and would love to upstream two pieces instead of carrying them in a fork. I've spiked both against `v1.9.0` (`222460f`) and wanted to ask whether you'd accept PRs, and in what shape.

### 1. Right-to-left layout and a Persian (`fa`) locale

tududi already ships Arabic strings, but the UI has no RTL handling, so `ar` renders left-to-right today. What I tried:

- **One line in `frontend/i18n.ts`**: `document.documentElement.dir = i18n.dir(lng)` on `languageChanged`.
- **A mechanical, idempotent codemod** from physical to logical Tailwind 3.4 utilities: `ml-*`→`ms-*`, `pr-*`→`pe-*`, `left-*`→`start-*`, `text-left`→`text-start`, `rounded-l`→`rounded-s`, `border-l`→`border-s`, plus `rtl:space-x-reverse`, `rtl:-scale-x-100` on chevrons/arrows, and `rtl:-translate-x-*` for toggles. No stack change, and LTR rendering is unchanged (logical utilities resolve to the same CSS in LTR). On the whole frontend that's ~877 automatic edits in ~190 files. The frontend Jest suite has the same results before and after.
- **About 20 hand fixes** for things a codemod can't see: chevrons rotated via inline `style.transform`, `paddingLeft`/`borderLeftColor` in inline styles, and `<bdi>` around user text so mixed-direction titles and `#hashtags` render correctly.
- A `fa` translation file (I'd maintain it).

I also noticed hashtag parsing is ASCII-only (`/^[a-zA-Z0-9_-]+$/` in `QuickCaptureInput`, `InboxItemDetail` and `inboxProcessingService`), so `#برنامه` or `#عربي` aren't recognised. A Unicode-aware pattern (`\p{L}\p{N}`) would fix that for every non-Latin language.

**Question:** would you take this as (a) one PR with the codemod run and a script to re-run it, or (b) split by area? Since the codemod touches many files, I'd want to time it to avoid conflicts with in-flight work.

### 2. Optional goal hierarchy: `parent_goal_id` and more horizons

Goals today are `season | year`. I'd like goals to nest (vision → 5-year → year → season → month → week) so a weekly goal can roll up into a seasonal one. The spike is purely additive:

- Migration: nullable `goals.parent_goal_id` (FK, `ON DELETE SET NULL`, indexed), nullable `period_start`, `period_end`, `achieved_at`. The ENUM gains `vision`, `five_year`, `month`, `week`. `season` stays the default, and existing rows are untouched (on SQLite it's `ADD COLUMN` only; on Postgres `ALTER TYPE … ADD VALUE`).
- Service rules, not DB constraints: a child's horizon must be shorter than its parent's, max depth 6, no cycles, parent must be visible to the same user.
- A roll-up query (`WITH RECURSIVE`, works on SQLite and Postgres) counting tasks reached directly (`tasks.goal_id`) or via projects. With 500 goals and 5,000 tasks it runs in ~11 ms for all goals and ~3 ms for one subtree on SQLite.
- The full backend suite stays green (+8 new tests), and the upgrade/schema-parity suite passes.

The UI part (picking a parent, showing children on the goal page) would come after, if you're open to the model change.

**Question:** does a goal hierarchy fit your vision for Goals, or would you rather keep goals flat? If flat is the intent, I'll keep this in my fork behind a clear `LTD-PATCH` marker and won't push it on you.

Thanks for tududi. Happy to adjust anything above to match how you want the codebase to evolve.
