## A-08 با کد و درخواست واقعی

کد: `backend/modules/tasks/core/builders.js` در `buildTaskAttributes` فیلدها را whitelist می‌کند و `uid` در آن نیست. `uid` را `defaultValue` مدل می‌سازد. هیچ middleware برای `Idempotency-Key` در `backend` وجود ندارد.

درخواست واقعی (Bearer، دو بار پشت سر هم، با `Idempotency-Key` یکسان):

```
POST /api/task  {"name":"A-08 probe","uid":"ltdclientuid0001"}  Idempotency-Key: ltd-a08-probe-1
→ HTTP 201  stored uid=anywi0bx6ykr13g id=6
→ HTTP 201  stored uid=h33ik4pm4ugzsx7 id=7
tasks named "A-08 probe": 2
```

نتیجه: `uid` کلاینت نادیده گرفته می‌شود و API idempotent نیست. هر تکرار درخواست یعنی رکورد تکراری.

## آزمون service worker با Chromium (Playwright 1.63) روی PWA واقعی

harness: `spike/g5:scripts/ltd/pwa-offline.mjs`. صفحه از یک proxy محلی (`:3020` ← `:3002`) باز می‌شود تا «سرور در دسترس نیست» و «سرور commit کرد ولی پاسخ گم شد» شبیه‌سازی شوند، بی‌آنکه خود tududi تغییر کند. SW واقعی v1.9.0 کنترل صفحه را داشت (`controlled: true`، `'sync' in registration: true`).

| سناریو | آنچه رخ داد (HTTP و IndexedDB واقعی) |
|---|---|
| **A** آفلاین مرورگر (`context.setOffline(true)`) | صفحه: `TypeError: Failed to fetch` (نه `202` مستند). در صف `tududi-sync-queue` یک ورودی ثبت شد. پس از برگشت آنلاین، در ۶۰ ثانیه replay نشد. سرور: 0 سطر. |
| **B** مرورگر آنلاین، سرور قطع (proxy اتصال را می‌بندد) | proxy: `refused POST /api/task`. صفحه: `TypeError: Failed to fetch`. صف: 2. پس از برگشت سرور و reload، در ۶۰ ثانیه replay نشد. سرور: 0 سطر. |
| **C** سرور commit کرد، پاسخ گم شد | proxy: `upstream committed, dropping response (201)` و بلافاصله `forwarded POST /api/task 201`. صفحه: `201`. **سرور: 2 سطر برای یک کنش کاربر.** صف SW دخالتی نداشت؛ تکرار، retry شفاف شبکهٔ مرورگر روی اتصال keep-alive بسته‌شده بود. |

کاوش پس از اجرا:

```
registration.sync.register('ltd-probe') → "UnknownError: Background Sync is disabled."
permissions.query('background-sync') → "prompt"
queued entries: [{ url: "/api/task", method: "POST", body: "", has_csrf_header: true, sessionId: "undefined" }, … ×2]
```

## یافته‌ها

1. **باگ از دست رفتن داده در صف آفلاین (upstream v1.9.0).** در `public/sw.js`، `handleApiMutation` اول `fetch(request)` را صدا می‌زند. این کار بدنهٔ `Request` را مصرف می‌کند. در شکست، `queueRequest(request)` با `request.text().catch(() => '')` بدنهٔ **خالی** ذخیره می‌کند. شاهد: هر دو ورودی صف `body: ""` دارند، در حالی که صفحه `{"name":"G5-A …"}` فرستاده بود. تأیید مستقل در Node:
   ```
   request.text() after fetch threw: TypeError Body is unusable: Body has already been read
   clone() before fetch keeps body: {"name":"x"}
   ```
   پیامد روی دستگاهی که Background Sync دارد: replay یک `POST` خالی می‌فرستد ← `400 Task name is required` ← ورودی پاک نمی‌شود (فقط `response.ok` پاک می‌کند) ← در هر sync دوباره تکرار می‌شود و متن کاربر از دست رفته است. رفع یک‌خطی است (`request.clone()` پیش از `fetch`) و برای PR به upstream مناسب است.
2. **تکرار بدون idempotency.** سناریو C نشان می‌دهد حتی بدون صف آفلاین، قطع پاسخ روی شبکهٔ ناپایدار موبایل یک کنش را دو بار ثبت می‌کند. این شاهد مستقیم برای ضرورت `ltd_idempotency_keys` و `uid` سمت کلاینت در فاز ۳ است (§13.5).
3. **iOS هیچ مسیر replay ندارد (از کد).** `queueRequest` فقط اگر `'sync' in self.registration` باشد `sync.register` را صدا می‌زند، و `replayQueuedRequests` فقط از رویداد `sync` اجرا می‌شود. Safari در iOS، Background Sync ندارد. پس نوشتن‌های صف‌شده روی iOS هرگز replay نمی‌شوند (نه با `online`، نه با بارگذاری صفحه).
4. **اگر `sync.register` رد شود، صفحه خطا می‌بیند.** `queueRequest` استثنای `sync.register` را نمی‌گیرد. در Chromium خودکار («Background Sync is disabled») `respondWith` رد شد و صفحه به‌جای `202`، `Failed to fetch` گرفت، در حالی که ورودی در صف نوشته شده بود.
5. **نگهبان «کاربر دیگر» کار نمی‌کند (`sessionId: "undefined"`).** `App.tsx` مقدار `notifySwSession(data.user.id)` را می‌فرستد، ولی `GET /api/current_user` در v1.9.0 فیلد `id` ندارد و فقط `uid` دارد (با درخواست واقعی بررسی شد). پس `String(undefined)` = `"undefined"` برای **همهٔ** کاربران فرستاده می‌شود و ورودی‌های صف همین مقدار را می‌گیرند. شرط `entry.sessionId !== sessionUserId` در `sw.js` هرگز برقرار نمی‌شود. روی دستگاه مشترک، نوشتن‌های صف‌شدهٔ کاربر A زیر session کاربر B replay می‌شوند. مشکل امنیتی کوچک و upstream است؛ با یافتهٔ ۱ یکجا رفع شود.
6. **محدودیت ابزار.** `setOffline` در Playwright درخواست صفحه را پیش از SW می‌بندد و Background Sync در Chromium خودکار غیرفعال است. پس **replay موفق روی هیچ مرورگری دیده نشد.** این قلم برای دستگاه واقعی باز است.
